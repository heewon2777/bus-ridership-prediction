# 프로젝트 개요

사용자의 현재 위치와 목적지를 입력하면 (1) 최단 경로를 계산하고, (2) 그 경로상 정류장에서 다음 버스를 탈 수 있는 확률을 계산하며, (3) 종합 소요시간과 확률이 낮을 때의 대안을 제시하는 웹앱 프로토타입.

결과물 형태: **웹앱 프로토타입** (1차는 샘플/모의 데이터 기반 인터랙티브 데모, 이후 실제 API 연동)
확률 계산 방식: **과거 데이터 기반 통계/머신러닝**

**프로토타입 데모**: https://claude.ai/code/artifact/3370da80-55d1-412e-ae48-f16f033192f8
**데이터 파이프라인/학습 스크립트**: bus_congestion_pipeline.py (사용자 전달됨)
**실제 지도 연동 프로토타입**: bus-predictor-real-map-react/ (React + FastAPI, 사용자 전달됨, 실행하려면 카카오 API 키 필요 — 5-3 참고)

# 1. 시스템 아키텍처

```
[사용자 입력: 출발지, 목적지]
        ↓
[경로 탐색 모듈] → 최단 경로 + 후보 정류장/노선 목록
        ↓
[실시간 버스 정보 모듈] → 정류장별 다음 버스 예상 도착시간
        ↓
[탑승 확률 모델] → ① 정시 도착 확률 × ② 좌석 여유(혼잡도) 확률
        ↓
[종합 리포트 생성] → 총 소요시간, 확률, 대안 제시
```

실제 서비스 단계에서는 정류장 실시간 정보 수집(백엔드 서버/스케줄러)이 필요하므로, 브라우저에서 직접 공공 API를 호출하는 구조보다는 **백엔드 프록시 서버**를 두고 프론트엔드는 그 서버와만 통신하는 구조를 권장한다 (API 키 노출 방지, CORS 문제 회피, 과거 데이터 축적 용이).

머신러닝 학습 자체는 웹앱 안에서 일어나지 않는다. 파이썬 환경(pandas/lightgbm)에서 오프라인으로 학습하고, 그 결과(모델 파일 또는 요일×시간대×노선별 확률을 미리 계산한 룩업 테이블)만 백엔드가 들고 있다가 웹앱 요청에 응답하는 구조다.

# 2. 추천 API 및 데이터 소스

## 2-1. 경로 탐색 (최단 거리 계산)
- **ODsay 대중교통 길찾기 API** ([lab.odsay.com](https://lab.odsay.com/guide/guide)) — 도보+버스+지하철을 조합한 대중교통 경로 탐색에 특화되어 있어, "출발지 → 정류장 → 하차정류장 → 목적지" 전체 구간을 한 번에 얻을 수 있음. 개인/학생 프로젝트에 무료 티어 제공. 이 프로젝트의 핵심 API로 가장 적합. 실 서비스에서는 사용자가 직접 등록한 출발지·목적지(주소 또는 좌표)를 그대로 이 API의 입력으로 넘기면 된다.
- 보완: 카카오맵/카카오모빌리티는 도보 전용 길찾기 API를 공식 제공하지 않으므로 ([카카오 데브톡 문의](https://devtalk.kakao.com/t/api/144235)), 도보 구간 단독 계산이 필요하면 ODsay 결과를 활용하거나 직선거리+보행속도(약 4km/h)로 근사.
- 실 서비스에서 사용자가 "내 장소"를 이름으로 등록하려면 주소/장소명을 좌표로 변환하는 지오코딩이 필요하다 (카카오 로컬 API의 주소 검색·키워드 검색으로 처리 가능).

## 2-2. 실시간 버스 도착정보
- **국토교통부 (TAGO) 버스도착정보 API** ([data.go.kr](https://www.data.go.kr/data/15098530/openapi.do)) — 전국 단위 정류소별 도착예정시간 제공. 전국 커버리지가 필요하면 1순위.
- **서울시 버스도착정보 API** ([data.seoul.go.kr](https://data.seoul.go.kr/dataList/OA-1091/L/1/datasetView.do)) / **서울시 버스운행정보 BIS API** ([api.bus.go.kr](http://api.bus.go.kr/contents/sub01/wisOpenApi.html)) — 서울 지역만 다룰 경우 응답 속도·필드가 더 상세함 (남은 정류장 수, 실시간 GPS 위치 등).
- 두 API 모두 "예상 도착시간"을 제공하지만 이 값 자체에도 오차가 있다는 점이 정시 도착 확률 모델 설계의 출발점.

## 2-3. 혼잡도 / 좌석 여유 데이터 — 정류장 단위 승하차 데이터가 핵심

처음에는 "노선별 혼잡도"·"노선별 차내 재차인원" 국토교통부 API를 학습 데이터 후보로 꼽았는데, 확인해보니 이름 그대로 **노선 단위 집계**일 가능성이 높고(정확한 필드 명세는 data.go.kr이 자동 수집을 막아두어 직접 확인은 못 함), 정류장별 세부 승하차 데이터는 아니었다. 정류장 단위 데이터는 서울 열린데이터광장에 별도로 존재한다.

- **서울시 버스노선별 정류장별 승하차 인원 정보** ([OA-12912](https://data.seoul.go.kr/dataList/OA-12912/S/1/datasetView.do)) — 노선·정류장별 일일 승차/하차 인원. 교통카드(선불·후불·1회용) 집계 기준이라 현금 승차는 빠진다.
- **서울시 버스노선별 정류장별 시간대별 승하차 인원 정보** ([OA-12913](https://data.seoul.go.kr/dataList/OA-12913/S/1/datasetView.do)) — 위 데이터를 시간대별로 더 쪼갠 버전. **월별 CSV로 2015년부터의 전체 이력을 한 번에 내려받을 수 있어**, 별도의 실시간 폴링 파이프라인 없이 바로 학습 데이터로 쓸 수 있다. 다만 실제로 2026년 7월분 CSV를 받아 열어보니, 컬럼 단위 자체가 "월 전체 합계"이고 "일자별"이 아니었다 — 자세한 내용과 이로 인한 설계 변경은 5-1 참고.
- **재차인원 직접 계산 아이디어**: 국토부의 완성된 혼잡도 API를 기다리지 않고, 이 승하차인원 데이터로 직접 재차인원을 복원할 수 있다. 한 노선의 정류장을 순서대로 두고 `재차인원(정류장 n) = 그 노선 시작점부터 정류장 n까지의 누적 승차인원 − 누적 하차인원` 으로 계산하면, 시간대·요일별 재차인원을 스스로 만들 수 있다. **(주의, 5-1에서 실제로 확인됨) OA-12913 CSV 자체에는 정류장 순번 필드가 없어서, 이 계산을 하려면 서울 TOPIS나 TAGO의 별도 API로 노선별 정류장 순서를 추가로 확보해야 한다.**
- **일반버스 vs 광역버스는 "정원"의 의미 자체가 다르다.** 광역버스(직행좌석버스 등)는 2014년 세월호 사고 이후 도입된 입석금지 제도가 지금도 시행 중이고(2023년 도로교통법 시행령 개정으로 전 차종 등록 승차정원 100% 이내로 강화됨, [나무위키](https://namu.wiki/w/%EA%B4%91%EC%97%AD%EB%B2%84%EC%8A%A4%20%EC%9E%85%EC%84%9D%EA%B8%88%EC%A7%80%20%EC%A0%9C%EB%8F%84)), 정원을 넘기면 정류장에 무정차로 통과한다 — 즉 정원이 곧 좌석수에 가깝고, 그 순간은 "혼잡"이 아니라 "탑승 불가"다. 반면 일반버스는 애초에 입석을 전제로 설계돼서 등록 승차정원 자체가 좌석+입석을 합친 훨씬 큰 숫자다. 서울시가 안내판에 쓰는 "좌석수의 1.5배 = 혼잡" 기준은 일반버스의 편의 지표에 가깝고, 광역버스에는 그대로 적용하면 안 된다. 그래서 데이터 파이프라인에서는 노선마다 `bus_type`(일반/광역)과 등록 승차정원을 함께 관리하고, 혼잡도 라벨링 임계값도 타입별로 다르게 둔다.
- **서울시 버스 혼잡도 정보** ([혼잡버스 안내](https://mediahub.seoul.go.kr/archives/1084218)) — 실시간 "여유/보통/혼잡" 3단계 정보. 위에서 직접 계산한 혼잡도 등급을 검증하는 대조군으로 쓸 수 있다. 다만 서울시가 2026년에 판정 기준(좌석수 1.5배)을 재정비했을 만큼([뉴스1 기사](https://www.news1.kr/local/seoul/5589589)) 이 라벨 자체도 절대적인 정답은 아니라는 점은 감안해야 한다.
- **국토교통부 노선별 혼잡도 API** ([data.go.kr](https://www.data.go.kr/data/15142068/openapi.do)) / **노선별 차내 재차인원 API** ([data.go.kr](https://www.data.go.kr/data/15142063/openapi.do)) — 서울 외 지역까지 다루게 될 경우의 보조 후보. 정류장 단위 세부 데이터인지는 실제 신청 후 응답 스펙을 확인해야 한다.

## 2-4. 정류장/노선 메타데이터
- **TAGO 버스정류소정보 / 버스노선정보 API** — 정류장 좌표, 노선별 정차 정류장 순서 등 정적 데이터. (5-1에서 확인된 대로, OA-12913만으로는 정류장 순서를 알 수 없어 이 API가 실제로 필요해졌다 — 아직 미착수.)
- 노선별 **버스 타입(일반/광역)**과 **등록 승차정원**은 별도로 조사해서 관리해야 한다 (자동차등록 정보, 운송사업조합 공개자료, 또는 차종별 일반적인 정원을 위키 등에서 근사).

# 3. 탑승 확률 계산 모델

## 핵심 아이디어 — 두 확률의 곱

"탈 수 있는 확률"은 서로 다른 두 조건이 모두 충족될 확률이다.

`P(탑승 가능) = P(정류장에 제때 도착) × P(그 버스에 자리가 있음 | 시간대, 요일, 버스 타입, 직전 버스 혼잡도 등)`

제때 도착해도 만차라 못 타는 경우와, 자리는 있어도 늦어서 놓치는 경우는 원인이 다르므로 대안 제시(다음 버스로 vs 다른 노선으로 vs 더 빨리 걷기)도 이 둘을 구분해야 정확해진다.

다만 이 곱셈 자체는 "두 확률이 서로 독립"이라는 가정을 전제로 한 근사이며, 이 가정이 실제로 얼마나 맞는지는 별도로 검증이 필요하다 — 자세한 내용과 향후 계획은 3-3 참고.

## 3-1. 정시 도착 확률 (timing)

- `T_user`(정류장 도착 시각)와 `T_bus`(버스 실제 도착 시각)를 비교한다. `P = P(T_user ≤ T_bus - 승차여유시간)`
- 1단계(규칙 기반): 여유시간 = API 도착예정시간 − 도보 소요시간. 즉시 구현 가능.
- 2단계(통계 기반, 프로토타입에 구현): 도보 변동성과 노선별 과거 도착 오차(표준편차)를 합성한 분산을 갖는 정규분포의 CDF로 계산. `P = Φ((버스도착까지 남은시간 − 도보소요시간 − 승차여유) / σ)`
- 3단계(고도화): 지연 분포의 평균/분산 자체를 요일·시간대·날씨 등으로 예측하는 회귀모델로 정교화.
- **참고 정확도**: XGBoost로 정류장 간 이동시간을 예측한 연구는 MAPE 약 12%를 기록했고([Zhu et al., 2022](https://www.hindawi.com/journals/wcmc/2022/3504704/)), 딥러닝 모델을 쓴 다른 연구는 평균 지연 8분짜리 노선에서 예측 오차를 36초까지 줄였다([arXiv:2303.15495](https://arxiv.org/html/2303.15495v3)). 다만 이런 수치는 GPS 궤적·신호등 정보·실시간 교통량까지 갖춘 연구 환경 기준이라, 개인 프로젝트는 처음엔 오차가 더 크게 시작해서 데이터가 쌓일수록 좁혀진다고 보는 게 현실적이다.

## 3-2. 좌석 여유(혼잡도) 확률 — GBM 채택, 버스 타입별 임계값 분리

같은 시간대·요일에 정류장에서 버스가 출발할 때 자리가 있었는지를 과거 데이터로 학습해 확률화하자는 아이디어를 검토했다. 결론은 다음과 같다.

- **데이터는 실제로 존재하며, 실시간 폴링 없이 바로 확보 가능하다.** 위 2-3의 서울시 정류장별·시간대별 승하차 인원 데이터(2015년~ 월별 CSV)로 재차인원·혼잡도를 직접 복원할 수 있어, 처음부터 몇 달을 기다리지 않고 바로 학습을 시작할 수 있다.
- **첫 모델은 LSTM이 아니라 그래디언트 부스팅(GBM: XGBoost/LightGBM)으로 결정.** GBM은 얕은 결정 트리 여러 개를 순차적으로 이어붙여, 각 트리가 이전까지의 예측 오차(residual)를 보정하도록 학습시키는 방식이다. 시간대·요일 효과는 "주기적 패턴"이지 반드시 "이전 시점에 종속된 시퀀스"는 아니어서, 시간을 sin/cos로 인코딩한 특성 + 요일 + 공휴일 + 날씨 + 정류장 순번 + 직전 1~3대 버스 혼잡도(lag 특성)만으로도 대부분 설명된다.
- **버스 타입(일반/광역)에 따라 혼잡도 라벨링 기준을 다르게 둔다.** 일반버스는 등록정원(좌석+입석) 대비 비율로 여유/보통/혼잡 3단계를 나누는 완만한 기준을, 광역버스는 입석금지로 정원 자체가 하드 컷이라 훨씬 촘촘한 임계값을 쓴다. `bus_type`도 모델의 특성으로 넣어서, 새로운 노선을 추가해도 "광역버스는 정원 근처에서 확률이 급격히 떨어진다"는 패턴을 일반화할 수 있게 했다. 합성 데이터로 파이프라인을 검증해보니 이 차이가 뚜렷하게 드러났다 — 광역버스는 출근 피크에 좌석 여유 확률이 23%까지 떨어지고 한산한 시간에는 100%에 가까운, 여유/혼잡 이분법에 가까운 패턴을 보인 반면, 일반버스는 러시아워에도 77% 정도로 완만하게만 낮아졌다.
- **참고 정확도**: 지금 설계와 거의 동일한 피처(15분 단위 시간대, 요일, 월, 직전 5~10개 정류장 승하차 인원, 날씨)로 혼잡도 등급을 예측한 연구에서 Random Forest 분류기의 F1 스코어가 노선에 따라 0.68~0.99로 나왔다([관련 논문](https://par.nsf.gov/servlets/purl/10229761)). 노선의 승하차 패턴이 뚜렷할수록(예: 출퇴근 시간에 항상 붐비는 간선버스, 또는 입석금지로 패턴이 더 이분법적인 광역버스) 정확도가 높고, 불규칙한 노선은 상대적으로 어렵다 — 그러니 처음엔 본인이 자주 타는, 패턴이 뚜렷한 노선 1~2개로 좁혀 검증하는 게 좋다.
- **LSTM/GRU는 이후 단계에서 검토.** GBM 베이스라인으로 설명 안 되는 시퀀스 잔차(예: 버스 밀집·bunching처럼 앞차 상태가 뒷차에 이어지는 효과)가 실제로 남는 것이 확인되면, 그때 최근 N대 버스의 흐름을 보는 가벼운 시퀀스 모델로 확장한다.
- **검증 시 주의**: 교통 데이터는 시간적으로 강하게 연속돼 있어 무작위 분할은 데이터 누수를 일으킨다. 반드시 시간 순서를 지켜 학습/검증을 분리해야 한다. 확률로 제시할 값이므로 모델 출력(GBM score 등)은 보정(calibration, 예: Platt scaling/isotonic regression)을 거치는 것이 바람직하다. 종합 확률은 두 하위 확률의 곱이라 오차가 누적되므로, "실제로 탔는지 여부"를 라벨로 한 최종 확률 자체의 보정도 별도로 검증한다.

프로토타입 데모는 위 GBM 특성 구조(시간대·요일·직전 버스 혼잡도·버스 타입)를 그대로 흉내 낸 로지스틱 함수로 좌석 여유 확률을 계산해, 실제 모델이 학습하게 될 관계(출퇴근 피크·주말 완화·버스 밀집 효과·일반/광역 하드 컷 차이)를 시연한다. 웹앱에도 광역급행버스 예시 노선(**M4434번**, 동탄2신도시 환승센터↔회사)을 추가해, 같은 화면 안에서 일반버스 3개(402·7014·143)의 완만한 곡선과 광역버스의 계단형(하드 컷) 곡선을 나란히 비교해볼 수 있다. M4434는 실제로 운행 중인 노선(화성여객 운영, 동탄2신도시↔강남역, 왕복 약 83.6km, 평일 배차 10~50분/주말 40~60분)이라 예시로서의 설득력을 위해 임의 번호(9711) 대신 이 번호로 교체했다 — 다만 웹앱상의 정류장 좌표·배차간격·정원(45석 가정)은 실제 노선 데이터를 그대로 가져온 것이 아니라 데모용 근사치다.

## 3-3. 곱셈(독립 가정)의 한계 — 버스 번칭(bus bunching)과의 상관관계

핵심 아이디어의 `P(탑승 가능) = P(정시 도착) × P(좌석 여유)` 식은 수학적으로 두 사건이 **독립**일 때만 정확하다. 일반적으로는 `P(A와 B) = P(A) × P(B|A)`이고, `P(B|A) = P(B)`가 성립할 때만 지금처럼 단순 곱셈으로 줄어든다. 지금 모델(웹앱 데모, `bus_congestion_pipeline.py`)은 이 독립 가정을 전제로 설계돼 있다 — 좌석 여유 확률은 시간대·요일·직전 버스 혼잡도(lag)만으로 계산되고, 정시 도착 확률 계산에 쓰이는 "이번에 올 버스가 배차간격 안에서 정확히 언제 오는가"라는 정보는 전혀 참조하지 않는다.

이 독립 가정이 현실과 어긋날 수 있는 대표적인 이유가 **버스 번칭(bus bunching)** 현상이다. 어떤 버스가 앞차와의 실제 간격이 평소 배차간격보다 벌어진 채로 오면(=상대적으로 늦게 옴), 그 사이 정류장마다 대기 승객이 더 많이 쌓여 있다가 한꺼번에 타면서 그 버스는 더 혼잡해지고 정차 시간도 길어져 뒤차와의 간격이 더 벌어지는 악순환이 생긴다. 반대로 바로 뒤따라오는 버스는 승객이 적어 한산하고 오히려 더 빨리 온다([Wikipedia: Bus bunching](https://en.wikipedia.org/wiki/Bus_bunching); [버스 번칭에 대한 종합 리뷰 논문, Transport Reviews 2024](https://www.tandfonline.com/doi/full/10.1080/01441647.2024.2313969); [실시간 혼잡도 정보를 활용한 번칭 완화 정책 연구, Transportation Research Part A 2021](https://www.sciencedirect.com/science/article/abs/pii/S0965856421001051)). 즉 "이 버스가 상대적으로 늦게 오느냐"와 "이 버스가 얼마나 혼잡하냐"는 같은 원인(직전 버스와의 실제 간격)에서 함께 나오는, 서로 상관됐을 가능성이 있는 값이다.

지금 모델에 구체적으로 대입하면: 정시 도착 확률 계산에 쓰이는 `busEta`(다음 버스까지 남은 시간, 배차간격 안에서 값이 결정됨)가 클수록 — 즉 그 버스가 배차간격의 뒤쪽에서 옴, 사실상 더 늦게 옴 — 실제로는 그 버스가 더 혼잡할 가능성이 높을 텐데, 지금 모델은 `busEta`와 좌석 여유 확률을 완전히 독립적으로 계산한다. 이 지점이 곱셈 가정이 실제와 가장 어긋날 수 있는 부분이다.

**결정한 방향 (2026-08-25)**: 지금 당장 데모의 곱셈 구조를 바꾸기보다, 실제 승하차 데이터가 쌓이면 두 확률을 각각 독립적으로 학습해서 곱하는 대신 **하나의 결합 모델**로 상관관계를 직접 검증하고 반영하기로 했다. 구체적으로는:

1. **정시성-혼잡도 상관관계 검증**: OA-12913(정류장별·시간대별 승하차 인원) 등 실 데이터를 확보하면, "직전 버스와의 실제 간격(지연 정도)"과 "그 버스의 혼잡도" 사이에 실제로 상관관계가 있는지부터 통계적으로 확인한다 (예: 상관계수, 또는 지연 구간별 혼잡도 분포 비교).
2. **상관관계가 확인되면**: 좌석 여유 확률 모델(GBM)의 입력 특성에 "직전 버스와의 간격/지연 정도"를 추가해, 정시성 관련 정보가 혼잡도 예측에도 함께 반영되도록 한다. 즉 `P(좌석 여유)`를 시간대·요일만이 아니라 그 순간의 지연·간격 정보에도 조건부로 만드는 것 — `P(B)`가 아니라 `P(B|A)`에 더 가까워지게 하는 접근이다.
3. **더 나아가면**: 두 하위 모델을 따로 학습해서 곱하는 대신, "정류장 도착 시각 + 그 버스의 혼잡도"를 함께 예측하는 하나의 결합 모델(또는 두 타겟을 동시에 다루는 멀티태스크 모델)로 전환해, 곱셈이 아니라 학습된 결합분포에서 직접 `P(탑승 가능)`을 뽑아내는 것도 검토한다.
4. 그 전까지, 즉 실 데이터로 검증하기 전까지는 지금의 "두 확률의 독립 곱셈" 방식을 **알려진 단순화(known simplification)**로 명시하고 유지한다 — 데이터 없이 상관관계의 방향과 크기를 임의로 가정해 보정하는 것은 검증되지 않은 또 다른 가정을 얹는 것이라 오히려 위험하다고 판단했다.

# 4. 종합 소요시간 및 대안 제시 로직

**종합 소요시간** = 도보(출발지→정류장) + 대기시간 + 버스 이동시간(ODsay 제공) + 도보(하차정류장→목적지)

**종합 탑승 확률이 낮을 때 (예: 40% 미만) 제시할 대안**
- 다음 버스(또는 배차간격만큼 뒤) 기준으로 도착 확률과 혼잡도를 함께 재계산한 시나리오
- 다른 정류장/다른 노선 조합 경로 (ODsay가 제공하는 대체 경로)
- 도보/자전거(따릉이 등 공공자전거)로 목적지까지 직행하는 경우의 예상 시간
- 택시 이용 시 예상 시간(대략적 추정)
- "더 빨리 걸으면" 정시 도착 확률이 얼마나 개선되는지 재계산 (혼잡도는 같은 차량이므로 그대로)

프로토타입 데모에는 위 대안 네 가지를 모두 실제로 구현해 두었다.

# 5. 프로토타입 구현 메모 (샘플 데이터 버전)

- 위치 17곳(고정) · 정류장 6곳 · 노선 4개(402, 7014, 143, M4434)로 구성된 가상의 동네 그래프를 만들고, 도보 엣지(장소↔정류장, 장소↔장소)와 버스 엣지(정류장↔정류장)를 모두 포함한 그래프에서 경로를 열거해 기대 소요시간이 최소인 경로를 선택 (환승 포함 최대 depth 5).
- **정시 도착 확률**: "다음 버스 도착까지 남은시간 − 도보 소요시간 − 승차여유"를 평균으로, 도보 변동성과 노선별 과거 오차(가상의 표준편차)를 합성한 분산을 가진 정규분포의 CDF로 계산.
- **좌석 여유 확률**: 사용자가 선택한 요일·시각을 기준으로, 출퇴근 시간대 가우시안 피크 + 주말 완화 계수 + 노선별 기본 혼잡도 + 직전 버스 혼잡도(lag)를 로지스틱 함수에 넣어 "만차 확률"을 구하고, 1에서 뺀 값을 좌석 여유 확률로 사용. 요일·시각을 바꾸면 실시간으로 재계산되어 시간대별·요일별 영향을 직접 눈으로 확인할 수 있다.
- **종합 확률** = 정시 도착 확률 × 좌석 여유 확률로 계산해 카드마다 "68% × 54% = 37%" 형태로 투명하게 보여준다. 단, 이 곱셈은 두 확률이 독립이라는 가정 위에 있으며, 그 가정의 한계와 향후 검증 계획은 3-3 참고.
- **일반버스 vs 광역버스 하드 컷 시연**: 노선마다 `busType`(일반/광역)을 두고, 좌석 여유 확률 계산의 노선별 파라미터(기본 혼잡도·출퇴근 가중치·직전 버스 영향·주말 완화 계수)를 `ROUTE_CONGESTION_CFG`로 분리했다. 일반버스 3개(402·7014·143)는 기존과 동일한 완만한 곡선을 유지하고, 실존 광역급행버스 **M4434번**(동탄2신도시 환승센터↔회사앞 정류장, 정원 45석 가정)은 출퇴근 가중치와 직전 버스 영향을 훨씬 크게 줘서 출근·퇴근 시간대엔 좌석 여유 확률이 1~3% 수준까지 급락했다가 그 외 시간·주말엔 90% 이상으로 튀어오르는 계단형 곡선을 보이도록 했다 — "정원이 차면 정류장을 무정차 통과해 아예 못 탄다"는 실제 제도를 화면에서 바로 체감할 수 있다. 정류장 카드와 지도 범례에도 노선별로 "일반 · 입석가능" / "광역급행 · 입석금지" 배지를 표시해 구분을 명확히 했다. 신도시 위치는 지도 반대편 구석에 배치해, 직접 걸으면 한 시간 넘게 걸리지만 M4434번을 타면 훨씬 빠르게 갈 수 있어 실제로 버스가 필요한 시나리오가 되도록 했다.
- **내 장소 직접 등록**: 검색으로 등록된 장소가 없으면 "지도에 새로 등록" 항목을 눌러 지도를 클릭하는 방식으로 등록한다 (5-2 참고). 등록한 장소는 점선 원으로 지도에 표시되고, 검색창 아래 태그 목록에서 개별 삭제도 가능하다. 새 장소는 기존 그래프 계산 로직(도보/버스 경로 탐색)에 자동으로 편입되므로, 사용자가 자신의 동네에 맞게 자유롭게 지점을 늘려가며 테스트할 수 있다. 실 서비스에서는 이 "등록" 동작이 곧 지오코딩(주소→좌표 변환) 호출로 대체된다.
- 브라우저 아티팩트는 보안 정책상 외부 API를 직접 호출할 수 없어, 위 값들은 모두 샘플 데이터로 계산된다. 실 서비스로 전환 시 백엔드에서 ODsay/TAGO/혼잡도 API의 실제 응답으로 대체하면 동일한 계산 구조(정시 도착 × 좌석 여유)를 그대로 사용할 수 있도록 설계했다.

## 5-1. 데이터 파이프라인 스크립트 (bus_congestion_pipeline.py)

사용자에게 전달한 파이썬 스크립트. 실제 CSV가 없어도 합성 데이터로 전체 흐름을 검증할 수 있고, 이제는 실제 OA-12913 CSV(2026년 7월분)로도 한 번 돌려본 상태다.

1. 승하차 인원 데이터 적재 (`generate_sample_ridership()` 샘플 / `load_real_ridership_csv()` 실제 CSV)
2. 정류장 순번 순서로 누적 승차-하차 → 재차인원 계산 (`compute_onboard_load`, 합성 데이터 전용 — 실제 데이터에서 못 쓰는 이유는 아래 참고)
3. `ROUTE_INFO`(노선별 버스 타입 + 등록 승차정원)를 기준으로 버스 타입별로 다른 임계값을 적용해 여유/보통/혼잡 라벨 부여 (`add_congestion_label`)
4. 요일·시간대(sin/cos)·직전 시간대 재차인원(lag) 등 피처 생성 (`add_features`)
5. 최근 14일을 검증셋으로 분리하는 시간 기준 분할 (`time_based_split`) — 무작위 분할 금지
6. LightGBM으로 학습, 정확도/F1/특성중요도 출력 (`train_model`)
7. 요일×시간대×노선별 확률을 미리 계산해 `congestion_lookup.json`으로 내보내기 (`export_lookup_table`) — 이 값을 프로토타입의 `congestionLogit()`/`capacityProbability()` 자리에 반영하면 실제 학습 결과가 웹앱에 그대로 표시된다.

샘플 데이터 기준 실행 결과: 정확도 96.0% / macro F1 0.842 (일반버스 3개 + 광역급행버스 1개 예시 노선, M4434). 예시 노선 번호를 9711 → M4434(동탄2신도시↔강남역, 실존 노선)로 교체했지만 로직·수치는 동일하다(라벨만 바뀐 것이라 결과에 영향 없음). 실제 데이터로는 노선별로 이보다 낮거나(불규칙한 노선) 비슷하게(패턴이 뚜렷한 노선) 나올 것으로 예상된다.

### 실제 OA-12913 CSV(2026년 7월분)로 처음 돌려본 결과

사용자가 실제 데이터를 다운로드해서 전달했다. 열어보니 예상했던 스키마와 세 가지가 달라서, 스크립트에 실제 데이터 전용 경로(`load_real_ridership_csv`/`approximate_onboard_from_boarding`/`add_congestion_label_real_relative`/`add_features_real`/`time_based_split_real`/`train_model_real`/`export_lookup_table_real`, 이를 묶은 `main_real()`)를 별도로 추가했다 — 기존 합성 데이터 경로(`main()`)는 그대로 남겨뒀고, `python bus_congestion_pipeline.py 실제파일.csv`처럼 인자로 실제 CSV 경로를 주면 자동으로 이 경로가 실행된다.

- **일자가 아니라 월 단위 집계다.** `사용년월`이 "202607" 같은 월 문자열이고, 각 정류장·시간대 값은 그 달 전체 합계다. 요일(dow)/평일-주말 구분을 이 파일 하나로는 만들 수 없다 — 서울 열린데이터광장에 요일별로 쪼갠 별도 버전이 있는지 찾아봤지만 확인되지 않았다. 대신 이 데이터셋은 2015년부터 월별 파일이 계속 쌓여 있으니(2026년 7월분까지 매달 갱신 확인), 여러 달을 모으면 최소한 "월별" 변동은 학습에 반영할 수 있다.
- **정류장 순번 필드가 없다.** 표준버스정류장ID/ARS번호는 노선 순서와 무관한 전국 공통 정류장 ID라서(실제로 402번 노선 데이터를 정류장ID 순으로 찍어보면 노선 순서와 무관하게 뒤죽박죽이었다), 원래 설계인 "정류장 순서대로 누적 승하차 = 재차인원"(`compute_onboard_load`)을 그대로 쓸 수 없었다. 정확한 순번은 서울 TOPIS(`getStaionByRoute`, api.bus.go.kr) 또는 국토부 TAGO(`getRouteAcctoThrouStaionList`, data.go.kr)로 별도 발급받아야 한다 — 둘 다 data.go.kr 서비스키가 필요해서, ODsay 키 발급과 비슷한 절차가 한 번 더 필요하다. 지금은 그 작업 없이, 정류장의 시간대별 승차인원 자체를 재차인원의 근사치로 쓴다(`approximate_onboard_from_boarding`) — 실제 재차인원(이전 정류장에서 타고 안 내린 사람까지 포함)보다 항상 낮게 잡히는 쪽으로 치우친 근사치라는 점을 감안해야 한다.
- **관심 노선 4개 중 402·143만 이 데이터셋에 있었다.** 402(110행)·143(114행)은 실제로 존재했지만(행 수는 왕복 정류장을 모두 합친 개수로 보인다), 7014는 서울시 전체 666개 노선 중에 아예 없었다 — 노선번호 표기(마을버스는 지역명이 붙는 등)를 다시 확인해봐야 한다. M4434는 경기도 관할(M버스) 노선이라 애초에 서울시 OA-12913 범위 밖이다 — 이 노선을 실 데이터로 쓰려면 경기데이터드림 등 별도 출처가 필요하다.
- **라벨링 기준을 실제로 돌려보고 한 번 바꿨다.** 원래 방식(정원 대비 재차인원 비율, `add_congestion_label`)을 실제 데이터에 그대로 썼더니, 정류장 하나의 일평균 승차인원이 버스 한 대 정원(80~90명)보다 항상 훨씬 작아서 97.5%가 "여유"로 몰렸고, 모델은 사실상 아무것도 학습하지 못했다(정확도 97.7%인데 macro F1은 0.329 — "보통"/"혼잡" 재현율이 0). 그래서 절대적인 정원 대비 비율 대신 **같은 노선 안에서 상대적으로 얼마나 붐비는지(백분위)**로 라벨을 다시 정의했다(`add_congestion_label_real_relative`). 그 결과 여유/보통/혼잡 비율이 의도한 대로 55/30/15로 맞춰졌고, 정확도 58.9% / macro F1 0.443이 나왔다. 샘플 데이터의 96%/0.842보다 훨씬 낮은 수치지만, 특성 중요도 1·2위가 `hour_sin`/`hour_cos`로 나온 걸 보면 "시간대에 따라 붐비는 정도가 달라진다"는 핵심 패턴 자체는 모델이 제대로 잡아낸 것으로 보인다. 다만 이 라벨은 "정원 대비 몇 %가 찼는가"가 아니라 "이 노선 기준으로 상대적으로 붐비는 시간대인가"라는 뜻이라, 원래 목표였던 "좌석이 있어서 탈 수 있는가"에 대한 직접적인 답은 아니다 — 정류장 순번을 확보해 진짜 재차인원을 계산하기 전까지는 이 지점을 **알려진 단순화**로 명시하고 유지한다.

향후 실 데이터 반영 시 3-3의 결정에 따라, `add_features`에 "직전 버스와의 실제 간격/지연 정도" 특성을 추가하고, 정시성-혼잡도 상관관계 검증 결과에 따라 `train_model`을 하나의 결합 모델(또는 멀티태스크 모델)로 확장하는 것을 다음 단계로 계획한다. 또한 정류장 순번을 TOPIS/TAGO API로 확보하면 지금의 상대적 백분위 라벨(`add_congestion_label_real_relative`) 대신 원래의 절대적 정원 대비 라벨(`add_congestion_label`)로 복귀하는 것이 다음 실 데이터 개선 과제다.

## 5-2. 검색 UX 및 시각 디자인 고도화

버튼(칩) 선택 방식이던 출발지·목적지 선택을 실제 지도 앱과 비슷한 "검색창 자동완성" 방식으로 바꾸고, 화면 전반의 시각적 완성도를 끌어올렸다.

- **장소 검색 자동완성**: 출발지·목적지를 검색창에 입력하면 등록된 장소 중 이름이 일치하는 곳을 최대 8개까지 드롭다운으로 보여준다(`searchPlaces()`). 실제 서비스에서는 이 함수를 카카오·네이버 지오코딩 API 호출(비동기)로 교체하면 같은 드롭다운 UI에 실제 주소 검색 결과를 그대로 연결할 수 있도록 함수 경계를 나눠 두었다 — **다만 이 프로토타입 자체는 여전히 로컬 데이터셋(아래 17개 장소) 안에서만 검색되고, 실제 주소를 검색하지는 못한다.** 브라우저에 게시되는 아티팩트는 보안 정책상 외부 API를 호출할 수 없기 때문이며, 실제 주소 검색은 백엔드 프록시를 둔 뒤에야 가능하다. (실제 주소 검색이 동작하는 버전은 5-3의 React+FastAPI 프로토타입에서 확인할 수 있다.)
- **장소 데이터셋 확장 (7곳 → 17곳)**: 검색이 그럴듯하게 느껴지도록 아파트·마트·영화관·헬스장·도서관·시장·은행 등 다양한 유형의 장소를 추가했다.
- **검색과 "내 장소 등록"을 하나의 흐름으로 통합**: 검색 결과에 없는 이름을 입력하면 드롭다운 맨 아래 "○○ 지도에 새로 등록" 항목이 나타나고, 이를 누르면 지도 위에 배너가 뜨며 클릭한 위치가 그 자리에서 검색 중이던 필드(출발지 또는 목적지)에 바로 선택된다. 기존에는 별도의 입력창 + 버튼으로 분리돼 있던 것을 한 흐름으로 합쳤다.
- **원형 확률 게이지**: 종합 탑승 확률과 정류장별 확률을 막대 대신 SVG로 직접 그린 원형 게이지(도넛 차트)로 표시해 한눈에 들어오게 했다. 정시 도착·좌석 여유 두 하위 확률은 여전히 막대 그래프로 남겨 계산 과정의 투명성을 유지했다.
- **버스 아이콘 배지**: 정류장 카드에 노선 색상의 원형 배지 안에 버스 모양 아이콘(인라인 SVG로 직접 제작, 외부 아이콘 라이브러리 미사용)을 넣어 어떤 교통수단인지 시각적으로 바로 알아볼 수 있게 했다.
- **종합 결과 카드 재구성**: 총 소요시간과 확률을 큰 원형 게이지 + 요약 문장("여유 있게 탈 수 있어요" 등)으로 재구성해 첫눈에 결론이 보이도록 했다.
- **출발 요일·시각 선택 UX 개선**: 시각 선택을 기존의 가로 막대(range slider) 방식에서 "지금/출근·08시/점심·12시/퇴근·18시/심야·22시" 프리셋 칩 + `−`/드롭다운/`+` 스테퍼 조합으로 교체했다. 요일 칩과 같은 디자인 언어를 써서 시각적 일관성을 유지했고, "지금"을 누르면 요일·시각이 실제 현재 시각으로 함께 초기화된다. 막대를 드래그해야 했던 기존 방식보다 원하는 시각(특히 프리셋에 없는 애매한 시각)을 더 빠르고 정확하게 고를 수 있다.
- **"종합 결과" 아래 산출 근거 패널 추가**: 4번 섹션(종합 결과) 바로 아래에 "이 결과는 어떻게 계산됐나요? 근거 보기" 토글을 추가해, 화면에 표시된 총 소요시간·확률이 정확히 어떤 계산에서 나왔는지 실제 값으로 재현해 보여준다. ① 구간별(도보/버스) 시간을 하나씩 합산해 총 소요시간이 되는 과정, ② 정시 도착 확률을 "여유시간 = 남은시간 − 도보 − 승차여유"부터 정규분포 CDF(Φ)까지 단계별로, ③ 좌석 여유 확률을 로지스틱 회귀식의 각 항(노선 기본 여유도, 출퇴근 가중치×혼잡계수×주말완화, 직전 버스 혼잡도 영향)을 모두 노출해 합산 로짓 → sigmoid → 만차 확률까지, ④ 최종적으로 ②×③=종합 탑승 확률까지 그대로 재현한다. 평소엔 접혀 있다가 필요할 때만 펼쳐보는 방식이라 화면이 복잡해지지 않으면서도, 요청 시 근거를 정확한 숫자로 확인할 수 있다. 이 작업 중 로짓 계산 함수(`congestionLogit`/`capacityProbability`)를 각 항(기본값·출퇴근 가중치·직전 버스 영향)을 분리해서 반환하도록 리팩터링했는데, Node.js로 24개 시간대 × 7개 요일 × 4개 노선 전 구간의 리팩터링 전후 출력을 비교해 완전히 동일함을 확인했다.
- **버그 수정**: 이 작업 중 결과 패널·배너 등 `hidden` 속성을 쓰는 요소들이 `.panel`/`.chip-group`의 `display:flex` 규칙에 덮여 페이지 로드 시부터 보여 버리는 CSS 버그를 발견해 `[hidden]{ display:none !important; }` 규칙으로 고쳤다. Playwright로 실제 브라우저 렌더링 스크린샷을 찍어 라이트/다크 테마 모두에서 확인했다.
- 지도 위 장소가 17곳으로 늘면서 라벨이 겹치던 부분들을 좌표 조정으로 정리했다(정류장 등 기존 노선 계산에 쓰이던 좌표는 최대한 건드리지 않고, 새로 추가한 장소들의 좌표만 재배치).

## 5-3. 실제 지도 연동 프로토타입 (bus-predictor-real-map-react/, React + FastAPI)

Claude Artifact로 게시된 웹앱 데모는 보안 정책(CSP)상 구글 폰트를 제외한 모든 외부 요청(지도 SDK, API 호출)이 원천 차단돼 있어, 그 안에서는 어떤 방식으로도 실제 카카오맵/지오코딩을 붙일 수 없다. 이 제약을 확인한 뒤, Artifact 밖에서 직접 실행하는 별도 프로젝트를 만들어 사용자에게 압축 파일로 전달했다. 처음에는 Node.js/Express + 순수 JS로 스캐폴딩했으나, 사용자가 프론트엔드는 React, 백엔드는 FastAPI(Python)를 쓰고 싶다고 요청해 같은 기능을 **React(Vite) + FastAPI**로 다시 만들었다. 이후 카카오맵·검색 연동을 실제로 켜본 사용자가 겪은 SDK 로드 실패(도메인 등록 위치 문제)와 검색 401 오류(REST API 키 문제)를 함께 진단해 해결했고, 곧이어 **ODsay 대중교통 길찾기 API**를 붙여 두 지점 사이 직선거리만 보여주던 것을 실제 도보+버스+지하철 경로로 대체했다.

- **구성**:
  - `backend/`(FastAPI) — `main.py`(`/api/config`, `/api/search`, `/api/route` 라우트 + 배포 시 `frontend/dist` 정적 서빙), `requirements.txt`, `.env.example`(카카오 JS 키/REST API 키/ODsay 키 설정 안내), `.gitignore`.
  - `frontend/`(React + Vite) — `App.jsx`(전체 화면 구성 + 경로 조회 트리거), `components/SearchField.jsx`(검색창 + 자동완성 드롭다운, 출발지/목적지 공용), `components/KakaoMap.jsx`(지도 렌더링 + 마커/직선 갱신), `components/RoutePanel.jsx`(ODsay 경로 조회 결과 — 총 소요시간·요금·환승 횟수·구간별 도보/버스/지하철 목록 — 표시), `lib/kakao.js`(카카오맵 SDK 동적 로드, 중복 로드 방지), `lib/geo.js`(하버사인 공식으로 두 지점 간 직선거리 계산, 참고용), `lib/route.js`(`/api/route` 호출 + 표시용 포맷 헬퍼), `vite.config.js`(`/api` 요청을 백엔드 8000번 포트로 프록시).
  - `README.md` — 카카오 디벨로퍼스 가입부터 키 발급, ODsay 키 발급, 개발 모드 실행(백엔드·프론트 서버 각각), 배포용으로 FastAPI 하나로 합쳐 서빙하는 방법까지 단계별 안내.
- **실제 지도**: 카카오맵 JavaScript SDK로 진짜 지도를 화면에 그린다.
- **실제 검색**: 카카오 로컬 API의 "키워드로 장소 검색"을 사용. REST API 키는 카카오 공식 문서가 권장하는 대로 브라우저에 노출하지 않고, FastAPI 백엔드(`/api/search`)가 `httpx`로 대신 호출해주는 프록시 구조로 만들었다. 반대로 지도 표시용 JavaScript 키는 원래 브라우저 노출을 전제로 한 키(카카오 콘솔에 등록한 도메인에서만 동작)라서 `/api/config`로 프론트엔드에 내려준다.
- **실제 경로 탐색 (ODsay)**: 출발지·목적지가 모두 정해지면 백엔드의 `/api/route`가 ODsay의 `searchPubTransPathT`를 호출해, 추천 경로 1건(총 소요시간·요금·환승 횟수, 도보/버스/지하철 구간별 소요시간·노선번호)을 돌려준다. ODsay 키도 REST API 키와 마찬가지로 서버에서만 쓰고 브라우저엔 노출하지 않는다. 다만 응답의 `trafficType` 코드(1=지하철, 2=버스, 3=도보로 매핑)는 여러 공개 자료에서 공통적으로 확인되는 값을 썼을 뿐, 이 환경에서 ODsay 서버로 실제 호출을 못 해봐서 직접 검증하지는 못했다 — 사용자가 실제 키로 처음 호출해볼 때 한 번 맞는지 확인해보는 것을 권장한다.
- **동작 확인**: 두 지점을 검색해서 고르면 지도에 마커가 찍히고, 참고용 직선거리와 함께 ODsay로 조회한 실제 추천 경로(소요시간·요금·환승·구간 목록)가 나온다.
- **경로를 지도에 그리기 + 정류장 ARS 번호 확보 (2026-09-09)**: `/api/route`가 ODsay 응답에서 소요시간·요금만 뽑고 나머지를 버리고 있어서, ① 경로를 지도에 그릴 좌표도 ② 실시간 도착정보를 조회할 정류장 ID도 없는 상태였다. 이 둘은 같은 응답(`subPath[].passStopList`)에서 함께 나오므로 한 번에 뽑도록 파싱을 확장했다(`_build_legs`).
  - 각 구간(leg)에 `path`(지도에 그릴 좌표 목록)와 `stations`(정류장 이름 + ARS 번호)를 담아 내려준다. 버스·지하철은 경유 정류장을 순서대로 잇고, 정류장 목록이 없는 도보 구간은 시작·끝 두 점만 잇는다. **알려진 단순화**: 정류장을 직선으로 이은 근사 경로이며, 도로를 따라가는 정확한 형상이 필요하면 ODsay `loadLane`을 `info.mapObj`로 한 번 더 호출해야 한다.
  - 프론트엔드(`KakaoMap.jsx`)는 이 `path`를 구간별 색으로 그린다(도보 회색 점선 / 버스 파란 실선 / 지하철 초록 실선). 경로를 못 가져왔을 때만 예전의 출발-목적지 직선으로 되돌아간다. 이 과정에서 조회 실패 시 이전 경로선이 지도에 남던 버그도 함께 고쳤다(조회 시작 시 결과를 먼저 비운다).
  - ODsay 응답은 좌표가 문자열로 오거나 필드가 빠지는 경우가 있어 전부 방어적으로 읽고, 그 동작을 `backend/test_route_parse.py`(5개)로 고정했다. 실제 응답 스키마 자체는 `backend/probe_odsay.py`로 따로 확인한다 — 이 스크립트는 `lane` 필드로 각 구간의 정체를 독립 추론해 `ODSAY_TRAFFIC_TYPE` 매핑과 대조하므로, 미검증으로 남아 있던 `trafficType` 코드 확인을 한 번의 실행으로 끝낼 수 있다.
  - 다만 이 작업 환경에서는 처음에 ODsay가 `[ApiKeyAuthFailed]`(공인 IP 미등록)로 막혀 실제 응답을 받지 못했다. 그래서 검증은 실제 응답 모양의 mock 데이터를 백엔드 파싱에 통과시켜 프론트엔드 화면까지 확인하는 것까지만 했다(요약·구간 목록이 정확히 표시됨).
  - **`[ApiKeyAuthFailed]` 재발과 안내 수정**: 사용자가 실제로 다시 이 오류를 겪었다. 8/25에 등록한 공인 IP와 지금 회선의 IP가 달라진 것이 원인인데, 화면은 "키가 설정되어 있는지 확인하라"고 안내해 원인을 가렸다. 회선(집/회사/핫스팟)이 바뀔 때마다 재발할 문제라서, 백엔드가 이 오류를 만나면 자기 공인 IP를 조회해(`api.ipify.org`, 오류 경로에서만, 3초 제한) "IP 허용 목록에 현재 공인 IP xxx.xxx.xxx.xxx를 등록하세요"라고 등록할 값까지 알려주도록 바꿨다(`_friendly_odsay_error`). 프론트엔드의 틀린 힌트("ODSAY_API_KEY 확인")는 제거했다.
  - **실제 응답 검증 (같은 날, IP 등록 후)**: 사용자의 실제 통근 경로(양재 → 동탄, 67분, 11구간 — 버스 2·지하철 3·도보 6)로 `probe_odsay.py`를 돌려 `trafficType` 매핑(1=지하철/2=버스/3=도보)이 **전 구간 일치**함을 확인했다 — 미검증으로 남아 있던 항목이 닫혔다. 같은 검증에서 두 가지를 더 알게 됐다. ① **도보 구간에는 좌표가 아예 오지 않는다**(`startX/Y` 없음). 가정했던 fallback이 빈 채로 도보 점선이 그려지지 않고 있었으므로, 도보는 앞 구간의 마지막 점과 뒤 구간의 첫 점을 잇고 맨 앞/뒤 도보는 요청한 출발지·목적지 좌표를 쓰도록 고쳤다. ② 버스 구간의 `lane`에 **지자체 노선 ID(`busLocalBlID`, 서울 9자리·경기 GBIS ID)와 버스 종류 코드(`type`)**가 온다. 실시간 도착정보 API가 노선을 이 ID로 지목하고 종류 코드는 일반/광역 구분에 쓰이므로 `lanes`로 함께 내려주게 했다. 참고로 ODsay 추천 1순위 경로는 이 구간에서 M4434 광역버스가 아니라 신분당선→경강선→GTX-A 조합이었다 — "버스 탑승 확률"이 주제인 앱이라면 ODsay의 `SearchPathType`(2=버스만)이나 복수 경로 표시가 필요할 수 있다(미결정).
- **사용자가 직접 겪은 문제와 해결**: 실제 실행 중 (1) "카카오맵 SDK 로드에 실패했습니다" 오류는 도메인을 콘솔의 다른 메뉴(카카오톡 공유용 웹 도메인 등)에 등록해서 생긴 문제로, JavaScript 키 밑의 도메인 등록 칸에 다시 등록해 해결했다. (2) 장소 검색이 401 Unauthorized로 계속 실패한 문제는 REST API 키 자체가 잘못 들어가 있어서였고, 백엔드가 카카오의 원본 에러 메시지를 그대로 돌려주도록 만들어 둔 덕분에 원인을 바로 특정할 수 있었다. (3) ODsay 연동 초기에 `AttributeError`로 500 에러가 나던 문제는 ODsay의 에러 응답이 `{"error": [...]}` 형태의 리스트로 올 수 있다는 걸 코드가 가정하지 못해서였고, 리스트/딕셔너리 둘 다 방어적으로 처리하도록 고쳐 해결했다. (4) 이후 겪은 `[ApiKeyAuthFailed]` 오류는 ODsay의 "서버" 플랫폼 키가 공인 IP 허용 목록 기반이라, 고정 공인 IP가 없는 개인 개발 환경에서 흔히 겪는 문제였다 — 사용자가 직접 해결했다.
- **검증한 것 / 검증하지 못한 것**: 백엔드는 `pip install` → 서버 기동 → `/api/config`, `/api/search`, `/api/route`(키 미설정 시 안내 메시지가 정확히 뜨는지, 네트워크 오류 시 서버가 죽지 않고 에러를 정리해서 돌려주는지)를 확인했고, 프론트엔드는 `npm install` → `npm run build`(빌드 오류 없음) → `npm run dev`로 개발 서버를 띄워 Playwright로 브라우저에서 설정 경고·검색 오류 메시지, 그리고 `/api/route` 응답을 흉내낸 가짜(mock) 응답으로 경로 요약·구간 목록 UI가 라이트/다크 테마 모두에서 정상 표시되는지까지 확인했다. 사용자는 실제 카카오 키로 지도·검색이 동작하는 것, 그리고 실제 ODsay 키로 경로 조회가 동작하는 것까지 직접 확인했다. 다만 `trafficType` 매핑(1=지하철/2=버스/3=도보)이 실제 응답과 정확히 맞는지는 아직 명시적으로 확인되지 않았다.
- **현재 위치를 출발지로 + 휴대폰(아이폰)에서 열기 (2026-09-09)**: "현재 내 위치에서 탈 수 있나"가 이 프로젝트의 원래 질문인데, 지금까지는 출발지를 검색으로만 고를 수 있었다. 출발지 검색창 옆에 **📍 현재 위치** 버튼을 달아 브라우저 geolocation으로 좌표를 받아 채우도록 했다(`lib/geo.js`의 `locateMe`, `SearchField`의 `allowCurrentLocation`). 사용자가 이 앱을 주로 아이폰 Safari에서 열 예정이어서, 그 환경의 제약을 함께 반영했다.
  - **HTTPS 필수.** 브라우저는 https가 아니면 위치 정보를 아예 내주지 않는다(PC의 `localhost`만 예외). 휴대폰에서 PC의 LAN IP(`http://192.168.x.x:5173`)로 접속하면 정확히 이 경우에 걸리므로, Vite에 `npm run dev:phone`(`--mode phone`) 모드를 추가해 HTTPS(자체 서명, `@vitejs/plugin-basic-ssl`) + LAN 노출을 켠다. 기존 `npm run dev`는 그대로다. 이 `https://<PC IP>:5173` 주소를 카카오 사이트 도메인에 추가로 등록해야 지도가 뜬다. 휴대폰의 `/api` 요청은 Vite 프록시가 PC 안에서 백엔드로 넘기므로 백엔드는 바뀌는 게 없다.
  - **위치를 못 잡았을 때의 설계**: 실패해도 앱이 막히지 않고 검색창이 그대로 대안이 된다. 실패 원인을 코드별로 사용자가 고칠 수 있는 말로 바꿔 버튼 아래 한 줄로 보여준다 — http 접속(→ dev:phone 안내), 권한 거부(→ 아이폰 설정 경로 안내, 재시도 안 함), 신호 없음/시간 초과(→ 고정밀 GPS가 실내에서 시간 초과되기 쉬우므로 저정밀 Wi-Fi·기지국 방식으로 자동 재시도 후 안내). 잡혔더라도 정확도가 300m보다 나쁘면 경고한다 — 정류장까지의 도보 시간이 확률 계산의 입력이라 몇백 미터 오차가 결과를 바꾸기 때문이다. 좌표→주소 변환(역지오코딩)은 붙이지 않고 "현재 위치"라는 이름과 정확도(±m)만 표시한다 — 지도의 점으로 위치를 확인할 수 있어 API 호출을 하나 더 늘릴 이유가 없었다.
  - **아이폰 화면**: viewport 메타·560px 이하 세로 배치는 이미 되어 있었고, iOS Safari가 16px 미만 입력창에 포커스하면 화면을 자동 확대하는 문제만 모바일 폭에서 입력창 글자를 16px로 키워 막았다.
  - `locateMe`의 분기(비보안 컨텍스트, 미지원, 재시도 조건, 오류 메시지)는 Node 내장 test runner로 `frontend/test/geo.test.mjs`(6개)에 고정했다(`npm test`). 실제 아이폰에서 인증서 경고 통과 → 위치 권한 → 좌표 수신까지의 흐름은 사용자가 직접 확인해야 한다.
- **실행 조건**: 사용자 본인 명의의 카카오 디벨로퍼스 계정(앱 생성 + JavaScript 키/REST API 키 발급 + 도메인 등록 + "제품 설정 > 카카오맵" 활성화) + ODsay LAB 계정(애플리케이션 등록 + 인증키 발급)이 필요하다. 이 키 발급과 도메인 등록·제품 활성화는 API 제공사 정책상 대신 해줄 수 없는, 사용자 본인이 해야 하는 절차다.
