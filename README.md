# 내가 과연 탈 수 있을까 — 실제 지도 연동 프로토타입 (React + FastAPI)

기존 웹앱 데모는 Claude Artifact로 게시돼 있어서, 보안 정책(CSP)상 구글 폰트를 제외한
어떤 외부 요청(지도 SDK, API 호출 등)도 브라우저에서 직접 할 수 없습니다. 그래서 가상의
동네 지도 + 로컬 검색으로 UX와 계산 로직만 시연했습니다.

이 폴더는 그 다음 단계 — **실제 카카오맵과 실제 장소 검색을 붙이는 작업**의 출발점입니다.
프론트엔드는 **React(Vite)**, 백엔드는 **FastAPI(Python)**로 구성했습니다.

## 이 프로토타입이 하는 일

- 실제 **카카오맵**을 화면에 띄웁니다 (카카오맵 JavaScript SDK).
- 출발지·목적지 검색창에 장소명을 입력하면, **카카오 로컬 API(키워드 장소 검색)**로
  실제 장소를 찾아 드롭다운으로 보여줍니다.
- 검색 결과를 고르면 지도에 마커가 찍히고, 두 지점을 모두 고르면 참고용
  직선거리를 함께 보여줍니다.
- 두 지점이 모두 정해지면 **ODsay 대중교통 길찾기 API**로 실제 도보+버스+지하철
  경로를 조회합니다. ODsay는 한 번에 여러 경로(보통 10~25개)를 추천 순으로 돌려주는데,
  **전부 받아서 칩으로 골라볼 수 있습니다** — 첫 번째가 추천 경로, 나머지는 대안(기획서
  4장). 칩을 고르면 총 소요시간·요금·환승 횟수, 구간별(도보/버스/지하철) 목록, 그리고
  **지도 위 경로선**이 함께 바뀝니다 (도보는 회색 점선, 버스는 파란 실선, 지하철은
  초록 실선; 버스·지하철은 경유 정류장을 순서대로 이어 그립니다). 경로를 못 가져왔을
  때만 출발-목적지 직선으로 되돌아갑니다.
- 버스 구간의 노선마다 **지금 시각의 좌석 여유 확률**을 배지로 보여줍니다. 값은
  `model/congestion_lookup_real.json` — 서울시 정류장별·시간대별 승하차 데이터로
  오프라인 학습한 GBM 결과(`model/bus_congestion_pipeline.py`) — 에서 노선 × 시각으로
  찾아옵니다. 아직 402·143 두 노선만 학습돼 있어 나머지는 "좌석 데이터 없음"으로
  표시하며, **없는 값을 추정치로 채우지 않습니다.** 광역·직행좌석버스(입석금지)는
  "광역(입석금지)"로 따로 표시합니다.
- 경로상 정류장의 이름과 **ARS 번호**, 버스 노선의 **지자체 노선 ID**도 함께 받아둡니다.
  다음 단계인 실시간 버스도착정보 조회가 이 값들로 정류장·노선을 지목하기 때문입니다
  (아래 "다음 단계" 참고).
- 카카오 REST API 키와 ODsay API 키는 브라우저에 절대 노출되지 않습니다. FastAPI
  백엔드가 대신 두 API를 호출해주는 프록시 역할을 합니다 (카카오 공식 문서도 REST
  API 키는 서버에서만 쓰라고 권장합니다).

## 준비물 1: 카카오 API 키 발급받기

1. [카카오 디벨로퍼스](https://developers.kakao.com)에 카카오 계정으로 로그인합니다.
2. "내 애플리케이션 → 애플리케이션 추가하기"로 앱을 하나 만듭니다 (이름은 아무거나, 예:
   `bus-predictor`).
3. 앱 생성 후 **앱 키** 메뉴에서 다음 두 개를 확인합니다.
   - **JavaScript 키** → 실제 지도를 그리는 데 씁니다.
   - **REST API 키** → 장소 검색(지오코딩)에 씁니다.
4. **플랫폼 설정**으로 이동해 "Web" 플랫폼을 추가하고, 사이트 도메인에
   `http://localhost:5173` (프론트엔드 개발 서버 주소)을 등록합니다. 나중에 실제
   서버에 배포하면 그 도메인도 여기에 추가해야 지도가 뜹니다.
5. (자주 놓치는 단계) 콘솔 왼쪽 메뉴의 **"제품 설정 > 카카오맵"**에서 카카오맵 사용
   설정을 켜야 합니다. 앱 키·도메인 등록이 맞아도 이걸 안 켜면 지도 로드가 403/인증
   실패로 계속 막힙니다.

## 준비물 2: ODsay API 키 발급받기

실제 도보+버스 경로(소요시간·요금·환승)를 조회하려면 [ODsay LAB](https://lab.odsay.com)
API 키도 필요합니다.

1. [lab.odsay.com](https://lab.odsay.com)에서 회원가입합니다 (카카오와는 별개의 계정입니다).
2. "애플리케이션 > 애플리케이션 등록" 메뉴에서 애플리케이션을 하나 등록합니다.
3. 등록하면 발급되는 **인증키(App Key)**를 `KAKAO_REST_API_KEY`와 마찬가지로 절대
   프론트엔드에 노출하지 않는 민감한 키로 취급해서, 아래 `.env`의 `ODSAY_API_KEY`에
   넣습니다.
4. 개인/학생 프로젝트용으로는 무료 사용량 제한이 있는 티어가 제공됩니다 — 정확한
   한도는 lab.odsay.com의 요금/정책 페이지에서 최신 값을 확인하세요.
5. 애플리케이션을 **"서버" 플랫폼**으로 등록했다면, 이 백엔드가 밖으로 나가는 **공인
   IP**도 함께 등록해야 합니다. 집·회사·핫스팟처럼 회선이 바뀌면 IP도 바뀌어
   `[ApiKeyAuthFailed]`가 나는데, 이때 화면의 에러 메시지에 **현재 공인 IP가 함께
   표시**되니 그 값을 ODsay 콘솔의 IP 목록에 추가하면 됩니다 (키는 그대로 두세요).

## 실행 방법 (개발 모드 — 터미널 두 개 사용)

### 1) 백엔드 (FastAPI)

```bash
cd backend
python -m venv .venv
source .venv/bin/activate        # Windows는 .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

`.env` 파일을 열어서 `KAKAO_JS_KEY`, `KAKAO_REST_API_KEY`, `ODSAY_API_KEY`를 방금
발급받은 값으로 채워넣은 다음:

```bash
python main.py
```

`Uvicorn running on http://0.0.0.0:8000`이 뜨면 백엔드 준비 완료입니다.
(`uvicorn main:app --reload --port 8000` 명령으로 실행해도 동일합니다.)

### 2) 프론트엔드 (React/Vite) — 새 터미널에서

```bash
cd frontend
npm install
npm run dev
```

터미널에 뜨는 주소(기본 `http://localhost:5173`)를 브라우저에서 열면, 실제 카카오
지도가 뜨고 검색창에 장소명을 입력하면 진짜 검색 결과가 나옵니다. 프론트엔드가 보내는
`/api/...` 요청은 `vite.config.js`의 프록시 설정을 통해 자동으로 백엔드(8000번 포트)로
전달되므로, 두 서버가 서로 다른 포트에 떠 있어도 별도 CORS 설정 없이 그냥 동작합니다.

## 휴대폰(아이폰)에서 열기 — "현재 위치" 버튼 쓰기

출발지 검색창 옆의 **📍 현재 위치** 버튼은 브라우저의 위치 정보(geolocation)를
씁니다. 브라우저는 **HTTPS가 아니면 위치 정보를 아예 내주지 않기** 때문에(PC의
`http://localhost`만 예외), 휴대폰에서 PC 주소(`http://192.168.x.x:5173`)로 그냥
접속하면 이 버튼은 무조건 실패합니다. 그래서 HTTPS로 띄우는 모드를 따로 뒀습니다.

1. PC와 휴대폰을 **같은 Wi-Fi**에 연결합니다.
2. 백엔드는 평소처럼 `python main.py`로 띄웁니다. 휴대폰이 보내는 `/api` 요청도
   Vite 프록시가 PC 안에서 백엔드로 넘겨주므로 백엔드는 바뀌는 게 없습니다.
3. 프론트엔드는 `npm run dev` 대신 **`npm run dev:phone`** 으로 띄웁니다. 터미널에
   `Network: https://172.30.1.139:5173/` 같은 주소가 뜹니다 (IP는 PC마다 다릅니다).
4. 그 주소(`https://` + PC IP + `:5173`)를 카카오 디벨로퍼스 **플랫폼 > Web > 사이트
   도메인**에 추가합니다. 등록하지 않으면 지도가 안 뜹니다. PC의 IP가 바뀌면(공유기
   재부팅 등) 다시 등록해야 합니다.
5. 아이폰 Safari에서 그 주소를 엽니다. 인증서가 자체 서명이라 "이 연결은 개인 정보
   보호 연결이 아닙니다" 경고가 뜨는데, **세부사항 보기 → 이 웹 사이트 방문**으로
   한 번 통과하면 됩니다. 통과한 뒤에는 https 페이지로 취급되어 위치 요청이 됩니다.
6. 📍 현재 위치를 누르면 Safari가 위치 권한을 묻습니다. 허용하면 출발지가 채워지고
   지도에 파란 점이 찍힙니다.

### 현재 위치가 안 잡힐 때

버튼이 실패해도 앱은 막히지 않습니다 — 검색창은 그대로 쓸 수 있으니 출발지를
검색으로 입력하는 것이 언제나 대안입니다. 실패 이유는 버튼 아래 한 줄로 표시되며,
원인별 해결 방법은 다음과 같습니다.

| 표시되는 안내 | 원인 | 해결 |
|---|---|---|
| "HTTPS가 아니라서…" | `http://` 주소로 접속함 | 위 `dev:phone` 모드의 `https://` 주소로 접속 |
| "위치 권한이 거부됐습니다" | Safari 위치 권한이 꺼져 있거나 이전에 거부함 | 설정 > 개인정보 보호 및 보안 > 위치 서비스 > Safari 웹 사이트 → "앱을 사용하는 동안" + "정확한 위치" 켬. 이 사이트만 거부했다면 주소창 "가A" 버튼 > 웹 사이트 설정 > 위치 → 허용 |
| "지금 위치를 알 수 없습니다" / "시간이 너무 걸립니다" | 실내·지하라 GPS/Wi-Fi 신호가 약함 | 앱이 자동으로 저정밀(Wi-Fi·기지국) 방식으로 한 번 더 시도합니다. 그래도 실패하면 창가로 이동하거나 검색으로 입력 |
| "±1.2km 정확도로만 잡았어요" (경고) | 잡히긴 했지만 부정확 ("정확한 위치" 꺼짐, 실내 등) | 지도의 파란 점이 실제 위치와 어긋나면 검색으로 바꾸세요. 정류장까지의 도보 시간이 확률 계산의 입력이라 몇백 미터 오차도 결과를 바꿉니다 |

경고를 통과했는데도 계속 "권한 거부"로만 실패한다면 인증서 자체를 신뢰시켜야
합니다: [mkcert](https://github.com/FiloSottile/mkcert)로 만든 인증서를 아이폰에
설치해 신뢰시키거나, ngrok/cloudflared 같은 터널로 진짜 인증서가 붙은 https 주소를
얻는 방법이 있습니다 (이 경우 그 주소를 카카오 사이트 도메인에 등록).

## 배포용으로 합쳐서 서버 하나로 띄우기 (선택)

개발할 때는 두 서버를 따로 띄우지만, 실제로 배포할 때는 프론트엔드를 빌드해서
FastAPI 백엔드 하나가 전부 서빙하게 만들 수도 있습니다.

```bash
cd frontend
npm run build        # frontend/dist 에 정적 파일 생성

cd ../backend
source .venv/bin/activate
python main.py        # frontend/dist가 있으면 자동으로 함께 서빙합니다
```

이 경우 `http://localhost:8000` 하나만 열면 되고, 이 도메인을 카카오 디벨로퍼스의
"플랫폼 > Web"에 등록해야 합니다. (실제 서버에 올릴 때는 그 서버의 도메인을 등록하세요.)
이 방식은 `http://`라서 휴대폰에서 "현재 위치" 버튼은 동작하지 않습니다 — 휴대폰용은
위 `dev:phone` 모드를 쓰거나, 실제 배포 시 HTTPS(도메인 + 인증서)를 붙여야 합니다.

## 왜 굳이 백엔드가 필요한가요?

- **REST API 키(장소 검색)**: 카카오 공식 문서에서도 REST API 키는 인증 정보이므로
  브라우저에 노출하지 말고 서버에서 호출하라고 안내합니다. 그래서 프론트엔드는
  카카오를 직접 호출하지 않고, 우리 백엔드의 `/api/search`만 호출합니다.
- **JavaScript 키(지도 표시)**: 이 키는 원래 브라우저에 노출되는 것을 전제로 하지만,
  카카오 디벨로퍼스에 등록한 도메인에서만 동작하도록 제한됩니다. 이 프로토타입에서는
  `.env` 한 곳에서만 관리하도록 `/api/config`로 내려주는 방식을 썼습니다 (키를
  프론트엔드 코드에 직접 하드코딩하지 않기 위해서입니다).
- **ODsay API 키(경로 탐색)**: 이 키도 REST API 키와 마찬가지로 브라우저에 노출되면
  안 되는 인증키라서, 프론트엔드는 우리 백엔드의 `/api/route`만 호출하고 실제 ODsay
  호출은 백엔드가 대신 합니다.
- Claude Artifact 안에서는 이런 서버 자체를 둘 수 없고, 브라우저에서 외부로 나가는
  요청도 전부 막혀 있어서 이번 작업은 Artifact 밖으로 나와야 했습니다.

## 다음 단계 (기획서 로드맵과 연결)

프로젝트 기획서(`docs/프로젝트_기획서.md`) 6장 로드맵 기준으로, 이 프로토타입 다음에
이어질 작업들입니다.

**1순위 — 실시간 버스도착정보 API 연동 (키 발급이 선행 조건, 본인만 가능)**

정시 도착 확률 `P(제때 도착)`의 유일한 입력값이라, 이게 없으면 확률 기능 전체가
나갈 수 없습니다. [data.go.kr](https://www.data.go.kr) 계정 하나로 인증키를 받아
아래를 활용신청하면 됩니다 (대부분 자동승인).

| API | 용도 |
|---|---|
| 국토교통부_(TAGO)_버스도착정보 | 정류소별 다음 버스 도착 예정시간 — 핵심 |
| 국토교통부_(TAGO)_버스정류소정보 | 좌표 → TAGO 정류소 ID 매핑 |
| 국토교통부_(TAGO)_버스노선정보 | 노선별 경유 정류소 순서 (아래 "정류장 순번"에도 필요) |
| 서울특별시 / 경기도 버스도착정보 | TAGO 커버리지가 비는 지역 보완. 같은 키 |

`/api/route`가 이미 정류장 **ARS 번호**와 노선의 **지자체 노선 ID**를 돌려주므로,
정류장·노선을 지목하는 부분은 준비돼 있습니다. 키가 생기면 `.env`에
`DATA_GO_KR_KEY=` 한 줄을 추가하는 것으로 시작합니다.

**2순위 — 탑승 확률 완성**

`P(탑승) = P(제때 도착) × P(좌석 여유)`. 좌석 여유는 이미 붙어 있으므로, 위 도착정보가
연결되면 정시 도착 확률(기획서 3-1의 정규분포 CDF)을 계산해 곱하고, 기존 Artifact
데모의 "근거 보기" 패널을 React로 옮겨 오면 완성된 형태가 됩니다.

**3순위 — 모델 품질 (기획서 5-1, 6장)**

- 학습된 노선이 402·143 둘뿐입니다. 실제로 타는 노선(서초08·H12·M4434 등)은 전부
  "데이터 없음"으로 표시됩니다. 서울 OA-12913에서 노선번호 표기를 다시 찾아보고,
  경기 노선은 별도 출처(경기데이터드림 등)가 필요합니다.
- 정류장 순번을 TOPIS/TAGO로 확보해 진짜 재차인원을 계산하면, 지금의 상대적 백분위
  라벨 대신 원래의 정원 대비 절대 라벨로 되돌릴 수 있습니다.
- 여러 달치 CSV를 모아 월별(가능하면 요일별) 변동을 학습에 반영.

**그 밖에**

- **경로를 실제 도로 형상으로 그리기(선택)**: 지금은 경유 정류장을 직선으로 이어
  그립니다. 정확한 도로 형상이 필요하면 ODsay `loadLane` API를 `info.mapObj`로
  한 번 더 호출해야 합니다.
- **출발 시각 선택**: 좌석 여유 확률이 지금은 "현재 시각" 기준입니다. 기획서의
  요일·시각 프리셋 UI를 옮겨 오면 "내일 8시에 탈 수 있나"도 물어볼 수 있습니다
  (단, 학습 데이터에 요일이 없어 시각만 반영됩니다).

## 검증한 것 / 검증하지 못한 것

확인한 것:

- **실제 ODsay 응답 (2026-09-09, IP 등록 후)**: 실제 통근 경로(양재 → 동탄, 67분·
  11구간·버스 2/지하철 3/도보 6)로 `python probe_odsay.py`를 돌려 `ODSAY_TRAFFIC_TYPE`
  매핑(1=지하철, 2=버스, 3=도보)이 **전 구간 일치**하는 것을 확인했습니다. 같은
  검증에서 **도보 구간에는 좌표가 아예 오지 않는다**는 사실이 드러나(가정했던
  `startX/Y` fallback이 비어 있었음), 도보는 앞 구간의 마지막 점과 뒤 구간의 첫 점을
  잇도록 고쳤습니다. 버스 구간의 `lane`에는 지자체 노선 ID(`busLocalBlID`)와 버스
  종류 코드(`type`)가 오는 것도 확인해 `lanes`로 함께 내려줍니다.
- **응답 파싱**: `python test_route_parse.py` 8개 통과 — 좌표가 문자열로 오는 경우,
  좌표 없는 도보 구간을 이웃·출발지·목적지로 잇는 경우, 좌표·노선 정보가 아예
  빠진 경우, 처음 보는 `trafficType` 코드가 온 경우 모두 예외 없이 처리됩니다.
- **전 구간 연결**: 실제 ODsay 응답 모양의 가짜(mock) 데이터를 백엔드 파싱에 통과시켜
  프론트엔드까지 흘려보내, 요약(`32분·1,850원·환승 1회`)과 구간 목록(도보 3분 /
  버스·143,402 14분 / 지하철·신분당선 11분 / 도보 4분)이 화면에 정확히 뜨는 것을
  브라우저 DOM에서 확인했습니다.

확인하지 못한 것 — 사용자가 자신의 환경에서 확인해야 합니다:

- **경로선이 지도에 그려지는 모습**: 실제 응답이 프론트엔드까지 도달하는 것은
  확인했지만, 카카오맵이 그린 선의 모양은 브라우저에서 눈으로 확인하지 못했습니다.

실제 응답 구조와 매핑을 재확인할 수 있습니다.
